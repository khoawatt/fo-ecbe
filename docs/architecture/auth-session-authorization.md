# Sessions and Account authorization

The Account remains the authentication principal. Login verifies credentials once through AccountService, creates an AccountSession, and returns an HS256 access JWT plus a separate refresh JWT. Refresh JWTs contain `sub`, `sid`, unique `jti`, `tokenType: refresh`, issuer, audience, issued-at, and expiry. The signing secret and audience differ from access JWTs. Only SHA-256 fingerprints of serialized refresh tokens are persisted. A successful refresh replaces the hash, expiry, and last-used timestamp atomically; a competing refresh with the old token receives 401. Logout atomically revokes only the current session and returns 204. Other sessions remain active.

Refresh TTL slides on every successful rotation. No absolute session lifetime is enforced yet. Old-token reuse is rejected but does not prove whether the cause was malicious replay or a concurrent client request. Access JWTs remain stateless and valid until expiration after logout or account disable. Client token storage and cookie/CSRF policy need a separate frontend security review.

Account self-service reads and updates the authenticated account from `request.user.id`. Ordinary updates permit email and phone only. ADMIN account routes use the JWT guard followed by the role guard. Permission metadata is evaluated against current normalized RolePermission relationships for the role-code snapshot in the access token. Role and permission checks do not prove ownership of a business resource; marketplace services must enforce ownership separately.
